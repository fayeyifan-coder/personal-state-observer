# P17｜证据签发公钥轮换与丢失恢复：隔离原型与放行门槛

日期：2026-10-28 · 仅供虚构密钥测试 · 不部署

## 背景和当前真实状态

- PR #14–#19 的服务端配对、独立审批、离线签名、可信申请凭证、Windows 自检均属于**尚未部署的草稿开发链**。其中只有早先的 iPhone **本机**密钥持久化与离线配对演练已在独立 Netlify 虚构测试站做过真机验收。
- PR #19 的 Windows 本机实测为 14 项离线自检通过。它验证了当前 Windows Node Crypto 能运行，但**没有**创建、注册或安装真实服务器/操作员密钥。
- 目前**不存在**已可信固定的真实服务器证据公钥。不能从未经独立核对的 JSON、Netlify 页面或 GitHub PR 里推断可信根。
- 用户真实个人历史仍仅保存在正式 iPhone Safari 的 GitHub Pages 来源下。本 PR 不得操作这个来源的 IndexedDB、Netlify Database 或正式 `main`。

## 本轮完成：只读的三方连续性审核

`tools/issuer-rotation-audit.mjs` 定义 `pso-issuer-rotation-attestations-v1`：

1. **旧服务器签发私钥**证明旧信任方同意更换。
2. **新服务器拟用私钥**证明新公钥的持有者确实能够签名。
3. **Windows 端独立操作员私钥**对同一份更换内容作人工授权。

三方签名均使用 ECDSA P-256 / SHA-256 原始 IEEE-P1363 64 字节，且覆盖同样的版本化字节串：站点 ID、现有公钥完整 SHA-256 指纹、新公钥指纹与坐标、随机 nonce、签发与截止时间。更换通知最长有效期五分钟。

审核者必须已经持有**以前独立核对过**的操作员 v2 清单，其签名已将旧服务器公钥绑定为原有信任。三方任一签名失效、旧密钥指纹不符、密钥没改变、站点错、凭证过期或清单已被替换，全部拒绝。

通过后只返回 `continuity-proven-no-trust-change` 的**审核意见**；不会写任何文件，不会更新 `operator-public.json`、服务器设置、数据库或设备身份，也不会批准任何手机。

## 为什么不做“自动一键换钥”

- **信任链连续性 ≠ 用户核准了生产变更**。三方证明即使全部成立，也必须通过第二渠道确认新公钥指纹，独立审核风险，作废旧签发能力，重新建立操作员可信绑定。
- **防重放没有服务器状态就不成立**。本模块不存储 nonce 或单调版本：重复审核同一未过期凭证可能再次得出“签名有效”，但因它完全只读，**不能**产生任何新的信任/权限。未来任何真正的轮换执行端必须有持久化唯一 nonce、版本递增与回滚拦截。
- **旧服务器签发私钥丢失**：三方连续性不可完成。必须停用相关新审批，用独立可信渠道重新建立服务器信任及操作员密钥；严禁把“旧钥匙找不到了”当作跳过旧签名检查的理由。
- **旧服务器签发私钥疑似泄露**：不能靠其签名证明安全，立即停止该签发身份并进行密钥轮换事故处置。使用独立操作者审核，而不是自动接受新 JSON。
- **操作员私钥丢失或疑似泄露**：停止新的批准和撤销操作，按事先设计的独立恢复和吊销流程核准新操作员公钥；不能因同一个 Netlify 账号登录就重获审批权。
- **新服务器私钥无法长期安全保存**：当前服务器函数接受注入的 `CryptoKey`，但这不代表 Netlify Functions 冷启动后会保留非导出私钥。正式上线前必须明确持久、安全的服务器密钥保管和加载方式及费用、限制，不能将临时生成的私钥误当永久服务密钥。
- **Windows 上明文环境、恶意程序或文件替换**：纯软件密钥与本地签名不足以防所有本机入侵，仍需 Windows NTFS ACL、独立备份和恢复演练。

## 验收门槛及后续阶段

- `tests/issuer-rotation-audit.test.mjs` 在 Windows/Linux 隔离 runner 上覆盖合法三方签名、伪造操作员签名、旧/新私钥错误、指纹与站点篡改、过期、旧版清单、错误来源以及**审核不修改原可信公钥**。
- 新增独立 GitHub Actions CI，同时复跑 PR #19 的公钥自检、PR #18 的可信申请证据和普通生产构建。
- **下一阶段应停止无限堆叠安全原型**：先汇总 PR #14、#16–#20 的依赖和未部署部分，做服务端受控入口、正式 Netlify Free 密钥持久化可行性及实际费用评估；仅在这些条件达成后，另外批准**虚构数据**的在线配对验收，再考虑真实数据同步。
- 正式部署之前还需要确定原始 `approveByOperator` 低层方法不能被未签名的 API 绕过，人工核对服务器证据签发公钥的真实来源、设备撤销后同步 CAS 发布挑战的即时失效、证据过期及丢失恢复安全审查。

## 当前结论

**隔离只读公钥轮换审核原型 PASS 才是本 PR 能给出的最高结论。** 实际服务器密钥轮换、首次信任、设备配对、Netlify Database 访问、上传个人历史均维持 **NO-GO**。绝不合入正式 `main` 或已发布虚构测试站分支。保留 iPhone 已经验证的测试 CryptoKey，不要求用户此时生成任何正式审批密钥。
