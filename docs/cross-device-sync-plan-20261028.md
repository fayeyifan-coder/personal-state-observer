# 个人状态观察器：手机主记录与跨设备同步计划（2026-10-28）

## 已确认的使用方式

- **手机是当前唯一的日常写入端**；电脑主要用于查看、分析和保留备份。
- 用户已经在手机成功恢复历史 JSON 备份。不要让后续开发自动替换手机数据库。
- 现有站点是 GitHub Pages 静态 PWA；Dexie / IndexedDB 数据属于当前浏览器和设备，没有现成的账户或云端同步。
- 当前 `restoreBackup` 是事务内清空三张表再写入，并非“增量合并”。旧版 JSON 中 `deviceData` 可以缺省。

## 第零阶段：先保护已经发生的记录

1. 手机上保持日常写入；电脑暂时不单独录入。手机定期导出 JSON，保留多个历史版本。
2. 导入任一备份前，必须允许用户先保存**目标设备的现有数据**，明确提示“覆盖”与“合并”不同。
3. 不允许将 GitHub 仓库、GitHub Actions 日志或前端源码当作存储个人状态明文数据的地方。
4. 手机历史数据、时期标记和设备 / 自测数据都属于同步范围；早晚阶段状态及 `null` 值必须原样保留。

## 第一阶段：安全差异预检（本 PR 仅交付纯函数与测试）

`compareBackupCollections(local, incoming)` **只读**比较三类数据：

- `DailyRecord` 按 `recordDate` 对齐（一天一条，含早晚阶段）。
- `DeviceDailyData` 按 `recordDate` 对齐（该数据表目前也按日期单独管理）。
- `PeriodLabel` 按稳定的 `id` 对齐。

结果将区分：本机独有、备份独有、内容相同、同一逻辑身份但内容不同、重复身份。属性顺序不同不应被误报为冲突。**不根据 `updatedAt` 自动判定哪一端正确**，也不丢弃一方独有的条目。

下一独立 PR 再把这一预检接到“数据”页，使用户先看到差异和危险项；仅在完成 UI 验收与备份保护后讨论导入策略。此阶段**不实现自动合并，不执行任何写入，不修改已有备份格式**。

## 第二阶段：可选的单向加密同步（待单独设计审查）

在手机唯一写入的前提下，可以先用“手机发布加密快照 → 电脑下载并核验”替代完整双向同步。服务端只保存密文与最少的版本元数据，不接受匿名读写；不上传明文答案、日期或时期名称。加密方案应使用现代、经过审查的 Web Crypto 协议和可靠的密钥派生；必须设计恢复密钥、凭据丢失、设备撤销及快照回滚的实际操作，而不是只加一个“加密”开关。

电脑默认使用**预览或只读镜像**，不能静默覆盖其 IndexedDB。云端需要版本历史、乐观并发检查和恢复路径；网络失败时不影响手机离线记录。后端选型、认证、密钥交付与费用在设计审查后单独确定，不能假设 GitHub Pages 已经提供后端。

## 第三阶段：可选双向同步（暂不启动）

只有在实际出现两台设备独立写入需求时再做。需要稳定设备 ID、实体级版本、删除墓碑、离线队列、幂等上传、冲突审查和跨设备时钟偏差处理。仅比较 `updatedAt` 或简单采用 last-write-wins 会在同一天早晚观察以及历史修改上造成静默丢失。

## 放行门槛

- 使用虚构样本验证：空设备导入、只有手机新增、两端各自新增、同日不同答案、时期标记修改、设备数据冲突、重复日期、旧版备份、离线及网络中断。
- 任何未解决冲突都不允许静默覆盖；清除数据必须要求明确、可恢复的操作。
- 先在独立分支执行 TypeScript 检查、纯函数测试、构建与真实手机浏览器验证，再由用户审阅决定是否合并。
- **禁止**在现阶段要求用户重新导入备份、清理浏览器存储、卸载 PWA 或关闭手机端日常记录。
