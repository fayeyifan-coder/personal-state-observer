# P13 · 独立离线审批签名：在权限变更前再加一道强制验证（2026-10-28）

## 为什么需要这一阶段

2026-10-28 用户已在 iPhone Safari 完成原测试 CryptoKey 的本机签名、跨刷新恢复和离线模拟配对申请，PR #15 已合并**虚构测试站**。PR #14 的真实 PostgreSQL 原型包含账户锁、待审核公钥、持有证明、人工批准与撤销，但它之前并没有可核验的**独立人工操作凭据**；`approveByOperator()` 只是一个还没有对外发布的服务端接口。这不能直接部署成浏览器按钮或普通 Netlify 登录的批准路由。

Netlify Private 的 `context.user` 能可信识别**账户**，不能证明调用的是哪个物理设备；同一账户可在电脑/iPhone 登录。因此不能用“Netlify 已登录”作为手机成为唯一写入端的授权依据。

## 本 PR 增加的独立操作因子

- `src/server/signedOperatorPairingGate.ts`：定义 `operator-pairing-action:v1` 的服务器侧 P-256 签名认证。
- 审批指令包括 `action`（批准/撤销）、Netlify siteId、ownerId、pending requestId、手机 deviceId、**完整公钥指纹**、随机 UUID nonce、签署时间、过期时间，字段按固定顺序逐行连接并签名。
- 每张指令最长有效期 **120 秒**，禁止跨站点、错账户、错设备、错公钥指纹、篡改操作类型、过期/过早的签名。
- **操作员公钥**必须由未来可信后端启动配置预先固定（这个仓库不提供正式密钥、不提供部署入口），绝不能从任何浏览器请求上传一个“审批公钥”就当成有效审批。
- 后端在核验独立审批签名后，才进入 PostgreSQL 事务；按用户最新 head 行 `FOR UPDATE` 序列化，再把 `nonce` 作为主键写入 `sync_operator_actions`，**同一张签名指令在多个函数实例上也只能成功一次**。**签名正确但审核对象不符的指令同样会消耗自己的 nonce**（用于防止同一错误指令反复试探）；操作者纠正指纹后必须生成新的短期指令和 nonce。
- 批准之前重新检查候选公钥指纹、持有证明、5 分钟申请期、同账户是否已存在授权手机；撤销之前重新计算当前发布设备公钥指纹、精确匹配 ID，撤销后废止剩余发布挑战，保留审批审计行。
- 代码无 Netlify Function/HTTP 路由，没有浏览器审批按钮，没有联网权限升级。单纯获取 Netlify 账号、普通 HTML、用户自报字段都不能调用这个操作。

## 文件与 CI

- `docs/sql-drafts/20261028203000_operator_signed_actions.sql`：只留在文档目录的**非自动迁移**审计表。
- `tests/postgres-operator-signed-gate.integration.ts`：GitHub Actions 本地一次性 PostgreSQL 16；随机**虚构操作员密钥**及手机密钥测试非法签名、跨账号/设备伪造、操作类型变更、过期、并发同一指令只生效一次、审批前无权限、撤销后挑战不可用、换机重新证明与再次审核。
- `.github/workflows/verify-operator-signed-pairing.yml`：原备份/加密/鉴权回归、TS 构建与真实 PG 集成测试。
- 正式主站 `main`、Netlify 已发布的合成站、用户 Netlify Database 都**不操作、不迁移**。

## 尚未完成，不能绕过

1. **独立离线审批工具与密钥保管**：本轮在 CI 中随机生成了操作员密钥来证明验证逻辑；还**没有**给用户的 Windows 电脑发放真实操作员私钥。以后需要独立于浏览器的本地签名工具，明确显示完整公钥指纹，要求人主动对比 iPhone 画面后签名。操作员私钥应受专门口令或本机凭据保护且能撤销/轮换。不能默认把“电脑能浏览”当作可以授权。
2. **管理员授权真实性**：后端只有验签逻辑，未来函数配置必须从可信管理员配置中读取**事先审核的公钥**。不能把操作员密钥放 GitHub、HTML、浏览器 JS、Netlify 函数环境明文或提交到聊天中。经本人确认的审核/撤销动作需要额外针对错误目标、替换设备、失窃机型做验收。
3. **正式可用的设备配对 API**：还没有将当前虚构 iPhone 既有密钥的申请真正提交到 Netlify、没有部署申请 API、公钥持有证明 API、审核受控入口或实际撤销。
4. **真实数据库迁移**：SQL 仍保留在 `docs/sql-drafts/`，官方 Netlify 自动迁移目录为空；不能在用户 Free 账户尚未批准上线费用和数据迁移前将它移到自动执行目录。
5. **原始 `approveByOperator`**：PR #14 里为证明数据库行为保留的低层操作仍存在，**不能直接暴露为任何对外 Function**。未来部署架构必须保证所有权限变更走新增的签名门禁，不能存在绕开的路由或代码路径。
6. **重放与中途失效**：审计 nonce 表验证跨实例幂等；要上线还需要完整失败恢复、超时、吊销审批公钥、审计 UI 及运维告警的单独评审。

**结论：仅完成隔离服务端的密码学审批门禁和真实临时 PG 验收。无真实设备登记、无云端上传、无需用户现在操作数据库或手机。**
