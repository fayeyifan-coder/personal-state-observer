# 个人状态观察器｜手机单向加密同步 P4 方案与放行门槛（2026-10-28）

## 本 PR 的范围

这是**协议基础 PR（#5）**，以 PR #3 的加密快照为底座；**不基于** PR #4 的虚构数据专用测试站，也不直接修改正式 `main`。目前没有可投入使用的云端同步接口，不能向用户宣称“已同步”。

新建 `src/services/syncProtocol.ts`，只提供纯本地（Web Crypto）操作：

- 从现有 `AppBackup` 创建 **AES-GCM 加密完整快照**，每个快照具有随机 UUIDv4 `snapshotId` 和上一个已确认快照的 `parentSnapshotId`。
- 同步版本链信息被**复制进经过 AES-GCM 身份验证的密文**。服务端可以根据明文外层的随机 ID 管理快照，但电脑解密后会核对内外版本链一致；任何只改外层父版本或快照 ID 的操作都会被拒绝。
- 只允许预定义的加密格式字段；拒绝把 `dailyRecords` 等明文字段藏入外层 JSON；限制可接受的密文体量。
- `assessIncomingSnapshot` 会区分本地已确认版本、候选新版本、来源历史未知和版本分叉/回退。所有新版本**只能进入“解密 → 差异预览 → 用户明确确认 → 事务内再核对”的既有恢复路径**。
- `canPreparePublish` 只检查本机与上次获取的云端版本是否一致，**不能替代服务端事务内的 CAS（比较并交换）**。
- 此 PR 中**没有** fetch/upload/download 自动化、计时器、后台任务、服务器地址、凭据、数据迁移或数据库清理。手机继续正常本地写入。

## 为什么选择 Netlify Identity + Netlify Blobs + 事务型版本索引

依赖现有 Netlify 用户习惯，而不是新增加一个托管商。但要区分：

1. Netlify **Private project** 保护的是整个测试站点的访客访问，不等于面向应用用户的手机/电脑身份认证。后续必须使用 **Netlify Identity** 或同等级登录系统，在服务器侧验证身份；**不能**只判断项目 Private、前端按钮、邮箱参数或客户端自报的用户 ID。
2. **Netlify Blobs** 适合存放每次完整加密快照：使用**站点级、按已验证用户身份隔离的不可变键**，开启强一致读，禁止前端直接指定其它用户的存储键，禁止覆盖已有快照。Blobs 的 `onlyIfNew` 能保护一个键不会被直接覆盖，但它不够完成整个“更新最新版本指针”事务。
3. 需要一个**具备事务/CAS 能力的索引存储**（可评估 Netlify DB / Postgres）维护每名用户当前 `headSnapshotId`、发布设备身份、单调服务器版本号、上传状态。完整快照写入 Blobs 后必须通过事务条件比较父版本与 head，不能仅以本机时间或 `updatedAt` 判断新旧。
4. 为避免仅成功上传 Blob、却未提交索引的中断导致丢失，后续设计需区分 `pending` / `committed`；孤儿密文可以安全重试或延后清理，但不能被错误地当成“最新成功版本”。
5. 暂定手机是**唯一发布设备**，电脑默认只能读取和预览；真正的写入授权应由服务端验证绑定的设备公钥、可撤销的设备凭据或经审查的等效机制。**同一账号的电脑登录不应自动获得发布权限**。

## 正式手机站点与 Netlify 之间的域名迁移阻断（新增）

**目前真实手机数据存放在 GitHub Pages 域名对应的 IndexedDB 中。** Netlify 域名是另一套浏览器 origin，浏览器不会自动共享数据，即使数据库名字相同也没有用。Netlify Identity 的网站会话 Cookie 也是 Netlify 站点的同域会话；不能假定目前 GitHub Pages 上的 PWA 能无障碍跨站使用其登录 Cookie，尤其是 Safari 可能阻止第三方 Cookie。

因此 P5 有两种合法选项，必须在实现前明确取舍：

- **方案 A（优先评估）**：将完整正式应用另行部署到与认证函数同域的 Netlify HTTPS 正式站点。先在新域名使用空数据库完成**真实备份导入前预览、显式恢复和数量校验**，手机旧 GitHub Pages 原站和旧备份继续保留。在至少一次完整恢复演练、用户确认所有历史记录可见之前，**不停止旧网站、不更改原始数据库、不启用自动同步**。独立测试项目 `cheerful-licorice-f4602a` **只允许虚构数据**，不得改造成正式数据站。
- **方案 B**：保留 GitHub Pages 作为正式前端，但另行设计跨域登录/受限 API 方案，并通过真实 Safari 验证授权、同源政策、跨站 Cookie 和离线行为。不能只打开 CORS 或把长效令牌硬编码在前端来绕过身份授权。

本 PR **只定义协议，不选择、更不执行**任何正式手机数据迁移。所有真实备份仍由用户自己保管。

## 加密与隐私约束

- 服务端只收到受保护的 `encrypted` 结构与随机版本链 ID，**不发送**明文每日记录、日期、时期标记、密码、密钥或原始 JSON。
- 原有加密备份使用 AES-256-GCM / PBKDF2-SHA256；低熵密码仍可能被攻击者在离线环境中猜测。上线前需设计适当的密码强度提醒、恢复密钥和密钥轮换。
- 版本链的加密认证不保证服务器不会删除历史，也不保证一台**从未见过任何历史版本的新电脑**能判断服务端给出的是否是最新版本。需在首次设备配对时确认锚点（例如双方显示的短校验信息），此后在每台设备保留最后可信任的版本。
- 即使服务端能强制身份认证，仍需登录限速、配对撤销、错误日志脱敏、跨站请求伪造防护、数据库备份与留存期。
- Netlify Blobs 不是 Netlify 的 HIPAA 合规存储方案；本项目仅为个人观察，不能声称符合医疗合规标准。
- 任何“最新快照”也不能静默覆盖电脑自己的 IndexedDB。电脑默认只读；若用户后来允许电脑写入，必须另立双向合并方案，不复用这个单向协议的判断当作双向无冲突保证。
